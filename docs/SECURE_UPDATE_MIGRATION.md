# P0-4｜更新の信頼基盤と旧bootstrapの移行計画

2026-11-15 時点の正式運用ゲート。**これは計画と現状の制約であり、更新署名の実装・実機合格を意味しません。**

## 現行の仕組みと限界

1. `voicepilot_bootstrap.py` が公式GitHub ReleasesからZIPをダウンロードし、GitHubのasset digest（SHA-256）とZIPの内容を検証します。
2. 次回起動時に更新ファイルを適用し、失敗した場合はバックアップを使って元に戻します。
3. 安定性を優先し、更新用の`voicepilot_bootstrap.py`と起動バッチは **自動更新で上書きしません**。v0.23.9の堅牢化が既存インストールに遡って有効になるわけではありません。
4. GitHubが提示するZIPとハッシュだけでは、GitHubアカウントや公開権限が侵害された際の真正性を独立検証できません。**現行更新は独立署名済みではありません。**
5. `BOOTSTRAP_SECURITY_REVISION = 2`は復旧処理のバージョン表示であって、署名の有効性や真正性の証明ではありません。旧bootstrapにはこの定数がないため、最新アプリ側で旧版の使用を通知します。

## v0.23.9で実装・CI検査する部分

- 変更前コードのバックアップ全体を**最初に**検査します。欠落・不正パス・シンボリックリンク・ハッシュ不一致・対象ファイルの型不一致があれば、復元の途中で不整合を起こさずに停止します。
- 新しいバックアップジャーナルに各ファイルのSHA-256を保持し、適用の直前にも更新ファイルのハッシュを再検査します。
- 新しい`last_good.json`を正常に記録する**前に**復旧ジャーナルを破棄しません。記録失敗時には旧コードへ復元し、誤ったロールバック先を示す記録を残しません。
- 旧形式の復旧記録は読み取り互換とします。ただし旧形式は個別ファイルのハッシュを持たないため、独立した完全性証明ではありません。
- これらの検査は一時ディレクトリ内のモックによるものです。Windows 11実機のスリープ・停電・ディスク満杯・アンチウイルス干渉等の合格ではありません。

## 署名付き更新に必要な今後の段階

1. **署名者の設定：** 開発者本人がオフラインの安全な場所でEd25519署名鍵を生成・保管します。秘密鍵はGitHub、ZIP、公開リポジトリ、テスト、CIログに一切登録しません。
2. **署名対象：** 公開用の`version`、ZIPのSHA-256、リリース識別子等を厳密な正規化形式でエンコードし、開発者の秘密鍵で署名します。署名はZIPと別の公開assetにします。
3. **検証の固定：** 信頼した開発者公開鍵を**不変のbootstrap**に事前埋め込みます。bootstrapが署名、ZIPハッシュ、リリースの単調増加、形式・サイズをすべて検証しなければ、ステージングも適用もしません。GitHubのハッシュだけの経路へ自動フォールバックしません。
4. **署名鍵の変更：** 現在の鍵から次の公開鍵への移行は旧鍵による署名済み承認が必要です。鍵の紛失・侵害時は更新を安全停止し、手動で信頼基盤を入れ直す方針です。
5. **旧bootstrapの移行：** すでに動作している旧bootstrapは新しい公開鍵を持たないため、**既存の自動更新だけで安全な信頼基盤へ移行したとは証明できません**。署名済み配布体制を作った後、開発者鍵の指紋を別経路で確認できる状態で、一度だけ明示的な手動移行を案内します。旧フォルダを残して別フォルダへ導入し、通常権限で起動・設定・Chrome連携を検証してから旧版を終了します。
6. **正式運用への判定：** 署名の正常系、改ざん、署名欠落、鍵違い、同一版のすり替え、ダウングレード、通信断、ディスク障害、更新中断、バックアップ破損、設定保持を試験。さらに通常権限のWindows 11実機で反復検証します。

### 利用者向けの現段階の判断

- 最新のアプリ`VERSION`が表示されていても、**旧bootstrapの更新チェックが新しくなるわけではありません**。
- 旧bootstrap警告がある場合は、署名検証が導入されるまで自動更新を高信頼なものとして扱わないでください。
- 暗号署名の検証と一度限りの移行手順が正式に用意されるまでは、重要な個人ファイルをVoicePilotから無人で更新・編集させないでください。
- 新しい署名鍵はこの文書には含まれません。自動で秘密鍵を作成してGitHubに保存する手順は導入しません。
